# obmem-gui

obmem's desktop control panel for macOS and Windows, built with Native Shell (NSH). It lists the projects obmem knows, shows each one's health and sets up agents. Notes are read and edited in Obsidian; the app deep-links there instead of rebuilding a note UI.

## Layout

The window is the sidebar's color. A strip along its top edge drags it and holds the sidebar's button after the system's window controls (`sidebar::top_strip`); under the strip, the page is one panel set into the window beside the sidebar (`widgets::page`). What the main area shows is `state::Screen`: a project (on one of its tabs), Review, or one page of the settings (`state::Section`). The sidebar lists Review, the projects and the way into the settings; while a page of the settings shows, it lists those pages and the way back instead (`state::leave_settings` returns to the screen they were opened from). A project's own settings stay on its tabs.

- `data.rs`: everything the window reads or changes, through obmem-core and obmem-agents. All of it blocks.
- `state.rs`: the window's signals and the actions that change them. Views call actions; actions run `data` on a blocking thread and write the result back. An action that a control waits for runs through `in_background_as` with a `Work` value, and `state::running(work)` says whether it is still running.
- `form.rs`: `Problems`, the rules a form's values break, by field. The rules themselves are obmem-core's (`ProjectSettings::problems`, `allowlist::problem`), or `data::connect_problems` for the one form that has no file behind it.
- `toasts.rs`: `done` and `failed`, and the `toaster` the root component places once. Built on nsh-base's `ToastManager`, `toast_stack` and `toast`.
- `sidebar.rs`: the sidebar in its two listings (`panel`, and `rail` when collapsed). It is resized by dragging its edge (`nsh_base::resize_handle`, as NSH's own dock does) and collapses to a rail of icons and initials, as narrow as the rail's own entries need, by its button in the top strip or by dragging it narrower than `SNAP`. Its edge shows nothing at rest and a line that fades toward both ends while the pointer is on it; width and collapsed state are kept with `nsh_core::storage::Storage`. Below `widgets::NARROW` it stays a rail and the full sidebar opens over the page as a drawer (`nsh_base::sheet`, which slides in and out over a scrim and closes on Escape). It is rebuilt when it lists something else (a `computed`), not for each page of the settings.
- `widgets.rs`: the shared pieces and the responsive rules: `page` (the panel: a bar that stays, a body that scrolls in a column of capped width), `page_bar` (title, what stands beside it, icon actions), `about` (what a page is about, above its blocks), `tabs` (pills under the bar), `icon_button` (named by a hint, with `.busy(..)`), `dialog_box` (a dialog over the window, see below), `choice` (a few options, all in sight), `select` (a list that opens from its trigger: the language), `switch_control`, `checkbox_control`, `callout` (a card with an inset color bar, which notices use), `field` (a row of a card's settings: the words at the left, a small control at the right), `input_field` (the same for a text box, which goes under the words, as wide as the card), `checked_field`, `problem_line` and `Marked` (an input field that shows the rule its value breaks), `FirstRow` (rows are parted by a hairline, and a card's first one takes `.first_row()` to have none above it), `action` and `primary` (buttons, with `.busy(..)` and `.blocked(..)`), `spinner` and `loading`. Layout follows `window()`, which is a signal: a `style_when(move || …window()…)` restyles as the window resizes.
- `motion.rs`: how the controls move. The durations, the curve and the press scales are named there once; a control takes `.washes()` (it only changes color under the pointer), `.presses()` with `.active(pressed)` or `.active(pressed_icon)` (it is pressed as a whole), or `.settles()` (it comes into place and leaves it), never a duration of its own. What comes into the window takes `.rises()` (a page's body, a notice, a dialog) or `.fades_in()` (a field's problem line). Native Shell runs none of it when the user asks for less motion.
- `themes/*.json`: the themes obmem ships, built into the binary (`appearance::BUILT_IN`). Each is a whole Native Shell theme file, shadcn's `cssVars` with a `light` and a `dark` section, plus the app's own tokens `ok`, `warn` and `highlight`, read with `widgets::tone`. `ink.json` is the default. `motoko.json` is drawn for obmem, and the rest are solyx's palettes. The status colors (`destructive`, `ok`, `warn`, `highlight`) are the same in all of them. A new one is a file there and a line in `BUILT_IN`.
- `appearance.rs`: the files behind the look, all blocking. The user's themes are the `.json` files in `themes/` next to the global config, in the same format, so a theme from tweakcn works as it is. `appearance.toml` beside it keeps the mode (`system`, `light`, `dark`) and the id of the theme each appearance shows. `tokens` makes the window's tokens of the two: every color has the light theme's light value and the dark theme's dark value. A theme that is gone or is not JSON shows the default instead.
- `state.rs` applies them (`start_appearance`): `set_color_scheme` for the mode, and an effect that calls `set_tokens` when a theme is picked, the theme files are read again, or the appearance shown changes. The theme files are read again when the Preferences page opens and when the window becomes active, so a file edited in another app shows on return. `appearance.toml` is read once, at start: the window's own state is the truth after that.
- `preferences_page.rs`: the Preferences page of the settings: the language, the mode, the theme each appearance shows, and the user's files with what is wrong with them. A theme is picked in a dialog (a `radio_group` of themes drawn in their own colors), where Duplicate copies the shown theme to the user's folder. There is no editor in the app: a theme is edited as a file.
- `locales/app.yml`: every text the user reads, in English (`en`) and Traditional Chinese (`zh`), in rust-i18n's format. `build.rs` reads it into the binary for builds by Cargo (`obmem_gui::root()` hands it to the engine); `nsh run` and `nsh package` read the folder themselves.
- `words.rs`: `tr!` and `named`, and the functions that say what obmem's libraries report (`Rule`, `Decided`, `ManualStep`, `Summary`) in the window's language. Its test fails when a key the code uses is missing from `locales/app.yml` in either language, when a key there is unused, or when a translation takes other arguments than its English.
- The language is a choice like the mode: `appearance::Language` (`system`, `en`, `zh`) in `appearance.toml`, applied with `set_locale` in `state::start_appearance` and `state::set_language`. System follows the computer through Native Shell's own matching.
- `icons.rs`: inline SVG icons in `currentColor`.
- `project_page.rs` (bar, tabs, Overview with the Claude Code import), `agent_tab.rs`, `sessions_tab.rs`, `settings_tab.rs`, `secrets_tab.rs`, `review_page.rs`, `preferences_page.rs`, `personal_page.rs`: views only.
- `private_vault.rs`: the button and the dialog that keep a project's memory in a private vault, outside the repo (`data::make_private`, which is `obmem init --private <folder>`). Two places offer it: the project's Settings tab, and the page of a project that does not load because its memory is private and this computer names no vault for it (`data::Unreadable::no_vault_here`, from core's `config::NoVaultHere`). The app does not set up a private vault's sync: that is `obmem init --private <folder> --bucket …` in a terminal.
- `personal_page.rs` has the settings' three pages about the personal vault: Personal vault (`config.toml`'s own settings), Sync (its status with Sync now, the `[sync]` settings through `settings::save_sync`, and connecting the device in a dialog whose secret and passphrase fields are `masked`, all through obmem-sync), and Allowed secrets (the personal allowlist).
- The Agent view shows the session-start context and `memory_context` output as plain text, exactly as an agent receives them. Rendering them as Markdown would merge lines and show something no agent sees.
- `login_env.rs`: on macOS, the PATH from a login shell (see below).

Logic another front end could use belongs in obmem-core or obmem-agents, not here.

## Text

- Text on screen is `tr!("key", name = value)`: a closure, so the text follows the language while it shows. Every shared piece that shows text takes `impl IntoReactive<SharedString>`. Pass a `String` only for what is data: a name, a path, a note's type or status, what a library's error says.
- Text said once is `t!("key")` when it is said: a toast, a notice, a dialog's title. A notice goes when the user leaves its screen, and the language is picked on another screen, so neither is ever seen in the wrong language for long.
- `t!` reads the window's language, so it runs on the engine thread only. `data.rs` runs elsewhere and returns typed values; `state.rs` and the views put them into words.
- A key names what the text is for, and a whole sentence is one key with `%{name}` arguments. A value such as a tab's label that a piece is given as a key (`widgets::tabs`, `choice`) stays a key until the piece shows it.
- A test id never comes from a label: it would change with the language.
- The reason an action failed is the library's English. Its title ("Could not read the session logs") is translated.
- Chinese is under the tag `zh`, not `zh-Hant` or `zh-TW`. Native Shell matches the computer's language by cutting a tag's last part off, and macOS says `zh-Hant-TW` where Windows says `zh-TW`: only `zh` is found by both. `nsh.json`'s `locales` names `zh-Hant`, which is what a package declares to macOS.

## How an action reports

Each outcome has one place, and a new action picks by this list:

- **A rule a field's value breaks** shows at the field: a red border and the reason under it. Nothing is sent. Build the form's `Problems` from a closure that reads its signals, pass `problems.at(field)` to `checked_field` and `problems.marks(field)` to the text box's `.marked(..)`, and send only when `problems.none()`. Problems show from the first try to send, then follow what is typed.
- **A rule only obmem can check,** because it needs the file system (where a private vault may be), shows at the field too, after the value was sent: `data` returns the rule as a value (`Ok(Err(rule))`), `state` keeps it with the value it is about (`state::vault_rule`), and the form's `Problems` reads that. The problem goes when the field changes.
- **An outcome that is one line, and any failure no field is to blame for,** is a toast: `toasts::done` goes by itself, `toasts::failed` stays until it is dismissed.
- **An outcome with more to read** (what `setup` changed, an audit's report, what an import did) is a `Notice`, shown on the page by `widgets::notice_area` until it is dismissed.
- **A flow done once, a pick among many, or a decision to confirm** is a dialog (`widgets::dialog_box`): connecting a device to sync, picking a theme, rejecting a finding. The page then shows one line and the button that opens it. The dialog sits in a `dynamic` that holds it only while a signal says it is open; a signal made with the page's content closes it when that content is read again, which is how a dialog whose work went through goes away.
- **While the work runs,** the button that started it is busy: `.busy(state::running(Work::..))`. It spins, keeps its size and takes no presses. `.blocked(..)` is for a button that must wait for another one's work (a review item's other decisions).

## NSH rules that bit

- After a failed save, do not reload the data the form was built from: the region rebuilds the form from the file and the user loses what they typed.
- A region re-renders whenever a signal it read changes. So each part of the state has its own signal, and a region that holds a form reads only what the form is built from. If it also read the notice, a failed save would rebuild the form and lose what the user typed. Seed a form's signals with untracked reads (`get_untracked`) for the same reason.
- A motion plays when it is made, so `.rises()` and `.fades_in()` play each time their element is built. Put them where a `dynamic` runs only when the element comes. A `dynamic` that reads what the element shows runs again with every change: read a `computed` of whether to show it instead, and let the element follow the rest itself (`widgets::problem_line`).
- `animate_layout` leaves a text of several lines at its old height when the change gives it more lines (a sidebar opening beside it): the text stays cut off. Do not animate a change that re-wraps text; the sidebar and the breakpoints change at once for this reason.
- A task started with `spawn` ends with its owner, and the button that starts one is usually re-rendered away when the task updates the page. Start tasks through `state::run_task` / `in_background`, which run them under the window's owner.
- `nsh_core::blocking` moves work off the engine thread. Every `data` call goes through it.
- Background loads must not change the screen. `state::select` picks a project quietly; only `state::open`, which the user triggers, switches to the project screen. Otherwise the project list, which loads after startup, pulls the user off Review or Personal settings.
- `ButtonElement` has no `test_id`, and neither has `ToastElement`. Wrap the button in a `view().test_id(..)` and select it with `id:… >> role:button`; a toast is found by its text.
- A border with a different color on one side is drawn with a square inner edge, `rounded_full` or not. A ring with a gap is an SVG (`icons::LOADER`), not a border.
- A timer started by a press ends with the button's owner, like a task. `toasts` runs its timer under the window's owner, and only while a toast is up.
- Folder dialogs, revealing a path and opening URLs are NSH services (`pick_paths`, `reveal_path`, `open_url`); no extra crate is needed.
- `#[native_module] fn native` runs in the runner's `main` before the engine starts any thread. It is the only safe place for process setup such as changing the environment, and `main.rs` calls the same `prepare_process` first.
- Apps opened from Finder get launchd's short PATH, without `~/.cargo/bin` or `/usr/local/bin`, so they would not find `obmem` or the Obsidian CLI. `login_env` adopts a login shell's PATH on macOS.
- Prefer `nsh_base`'s controls over drawing one from views: `tabs`/`tab`, `toggle_group`/`toggle`, `select`, `switch`, `checkbox`, `button`, `input`, `resize_handle`, `sheet`. They bring the accessibility role, keyboard handling and native motion (the tab underline travels), and leave the look to the app: style their parts with the `*_class` props, which take Tailwind classes that name the theme's tokens (`bg-primary`, `checked:translate-x-4`). A slot prop is a builder method (`checkbox().indicator(..)`). Tests select them by role: `role:tab[…]`, `role:switch`, `role:checkbox`, and `role:combobox` then `role:option[…]` for a select, whose list is outside the card that holds its trigger. A dialog's parts are found under its own id (`id:sync-connect >> role:button[Connect]`), and `common::open_settings` opens a page of the settings.
- `ButtonElement` has no `tooltip` either (only views do, through `Interactive`): `widgets::WithHint` wraps an element in a view with an `nsh_base::tooltip()`.
- The window has no system title bar (`current_window().set(..)` with a `TitleBarStyle::Hidden` title bar, in `App`). `sidebar::top_strip()` runs along the window's top edge: it drags the window, leaves room for the window controls and holds the sidebar's button after them (buttons in a drag region still take presses). The drawer has one of its own, since it covers the window's. Where the system draws its own title bar `title_bar()` is all zeros (the headless tests too), so the strip has a height of its own to fall back on.
- A nsh-base control's `accessibility_label` is a prop of `Option<SharedString>`: it takes `named("key")`, not `tr!`. A view's takes either.
- In `locales/app.yml`, YAML reads a bare `on`, `off`, `yes` or `no` as true or false, as a key too. Name a key something else (`switched_on`).
- Headless tests run in English. `common::start_in(Some("zh-Hant-TW"))` starts the app on a computer in that language (`EngineConfig::pinned`).
- Headless tests default to a phone-sized viewport. Set `config.viewport` to a desktop size, or the page column collapses to zero width and its text vanishes from `screen()`.

## Looking at the real window

The headless tests see text and roles, not pixels. To look at a change, run the built app against a throwaway config and capture only its window, without taking the keyboard or the pointer from whoever is at the machine:

- Start it with `OBMEM_CONFIG=<temp>/config/config.toml target/debug/obmem-gui`. The project list (`projects.toml`) is read from next to that file, so the real one is not touched.
- Press a control through System Events by its `description`, which holds the label (`name` is empty): `tell process "obmem-gui" to click (first button of window 1 whose description is "Save")`. A dialog is a `group` of the window, and takes the presses while it is open: `click (first button of (first group of window 1) whose description is "Done")`. A tab is a `radio button` of the `tab group`, and a select is a `combo box`, whose press opens its list.
- Typing needs the focus, so do not type: put the values a form should start with in the files it reads.
- Capture with `screencapture -x -o -l <window id>`. The id comes from `CGWindowListCopyWindowInfo`, filtered by the process id.

## Commands

- `cargo test --workspace` runs the headless flow tests in `tests/gui/`. They point `OBMEM_CONFIG` (and, for the Claude Code import, `HOME`) at a temp folder, so the real project list, vaults and `~/.claude` are never touched. That environment is process-wide, so `common::sandbox` reruns each test alone in a child process of the same binary. Add a test as a module of `tests/gui/main.rs`, not as a new file in `tests/`: every test binary links all of Native Shell, about 200 MB.
- Prefer `--workspace` to `-p obmem-gui`. `rmcp` turns on serde and serde_json features only when obmem-mcp is in the build, so the two commands build Native Shell twice, under different hashes, and `target/` keeps both.
- `cargo run -p obmem-gui`: the window on this machine.
- `nsh run` / `nsh package --target macos|windows`: run these inside `apps/obmem-gui`. Output goes to `.nsh/` under the current directory, and runner builds use `apps/obmem-gui/target` (several GB).
- The nsh CLI builds against NSH crates of its own version. Upgrade it together with the `nsh-*` versions in the root `Cargo.toml`. NSH needs the latest stable Rust.
